# M4 — bounded WebSocket market-data feed

**Status:** normative v1 contract
**Requirement author:** trade-rs M4 requirements crewmate
**Date:** 2026-09-25
**Scope:** M4 only — live trade, BBO, and bounded L2 market data from the in-memory engine

## 1. Purpose and authority

M4 adds a read-only WebSocket market-data boundary to the existing `trade-http`
process. It does not change matching, M2 event meanings, the M3 HTTP command/query
contract, or the single-writer ownership model.

The words **MUST**, **MUST NOT**, **SHOULD**, and **MAY** are normative. This contract
incorporates and is subordinate to:

- [the roadmap](../ROADMAP.md), which requires trade ticks, BBO updates, L2 snapshots,
  detectable loss, resynchronisation, and bounded slow-consumer handling;
- [the M2 requirement](M2.md) and [M2 scenarios](../scenarios/M2.md), which define the
  deterministic command/effect order and `trade_executed` meaning;
- [the M3 requirement](M3.md), [M3 scenarios](../scenarios/M3.md), and
  [HTTP contract](../HTTP.md), which define bounded non-waiting admission, queue-order
  barriers, HTTP errors, graceful engine drain, and the unchanged `GET /book` surface;
- [ADR-0003](../adr/0003-concurrency-model.md), under which one engine thread owns and
  writes every book;
- [ADR-0006](../adr/0006-monolith-first.md), under which M4 remains in one process with
  no new infrastructure; and
- [ADR-0007](../adr/0007-multi-symbol-single-thread.md), under which symbol books remain
  isolated behind the one engine writer.

The independently authored [M4 acceptance inventory](../scenarios/M4.md) is identified
by its exact scenario IDs in section 13. This requirement resolves the protocol choices
intentionally left open by those scenarios. The requirement author and scenario author
are independent as required by [the delivery contract](../DELIVERY.md).

## 2. Required outcome

M4 MUST expose one WebSocket endpoint on the existing HTTP listener:

```text
GET /market-data?symbol=<symbol>
Sec-WebSocket-Protocol: trade-rs.market-data.v1
```

One successful connection subscribes to exactly one configured symbol and receives:

1. exactly one authoritative initial top-N L2 snapshot;
2. zero or more live trade ticks;
3. final command-boundary BBO updates; and
4. final command-boundary top-N L2 snapshots when that visible projection changes.

Every live item is a separate UTF-8 JSON text frame. All three live record types share
one contiguous sequence series for the connection's symbol. The initial snapshot
establishes the current position without consuming a sequence value.

M4 is a live, lossy-by-disconnection feed, not a replay service. A gap, stream change,
decode error, socket loss, or server close invalidates continuity. The only M4 recovery
path is a fresh connection and its new queue-ordered initial snapshot.

## 3. Ownership and publication order

The engine thread MUST remain the only authority that:

- reads mutable book state for market-data publication;
- derives and caches the current BBO and configured-depth L2 projection;
- assigns market-data sequence values; and
- creates a receiver at the subscription barrier.

No WebSocket task may read or mutate a live book. No socket operation, async wait,
client loop, or JSON encoding may execute on the engine thread. M4 MUST NOT add a
second mutable book, shared-book lock, or asynchronously updated market-data replica.

After each successfully processed M2 command, the engine MUST logically publish for
that command in this exact order:

1. one `trade` for each M2 `trade_executed`, preserving M2 effect order;
2. exactly one final `bbo` if and only if the post-command BBO differs from the prior
   post-command BBO; then
3. exactly one `l2_snapshot` with `reason: "update"` if and only if the final visible
   top-N projection differs from the prior visible top-N projection.

The sequence assignment and non-waiting ring send attempts MUST finish before the
command's M3 completion one-shot is delivered. This orders market-data publication
before the corresponding HTTP completion without claiming that any peer has received
the bytes.

Rejected commands emit no market-data item and consume no market-data sequence.
Successful commands that produce no trade, BBO change, or visible top-N change also
emit nothing. A mutation strictly below configured depth remains outside v1 until it
changes the visible projection.

## 4. Subscription and handshake

### 4.1 Request shape

The request MUST use HTTP/1.1 `GET` on `/market-data`, contain no body, and contain
exactly one query key named `symbol`. Unknown, missing, or duplicate query keys are
malformed. Query decoding and scalar semantics MUST match M3:

- strict UTF-8 percent decoding and form-style `+` as space;
- a nonempty decoded string;
- no trimming, case folding, Unicode normalisation, or alternate-symbol substitution;
  and
- exact byte-for-byte lookup in the configured symbol registry.

The request MUST be a valid WebSocket upgrade and MUST offer exactly one parsed
subprotocol token: `trade-rs.market-data.v1`. A successful `101 Switching Protocols`
response MUST echo that exact token. Compression negotiation, including per-message
deflate, MUST be disabled.

The request target is the complete subscription. There is no JSON subscription frame,
acknowledgement frame, dynamic subscribe/unsubscribe operation, stream filter, or
multi-symbol connection in v1. The initial L2 snapshot is the successful subscription
acknowledgement. Closing the connection is the only unsubscribe operation.

### 4.2 Admission order and failures

Before returning `101`, the service MUST:

1. validate route, method, query, upgrade, and subprotocol;
2. acquire one market-data connection permit without waiting;
3. attempt exactly one non-waiting insertion of a `Subscribe(symbol)` barrier into the
   existing bounded engine queue; and
4. receive the barrier result containing the initial snapshot and receiver.

The barrier is an admitted M3-style queue item but not an M2 command. It consumes no M2
command index and no market-data sequence. Capacity failure MUST NOT wait, retry, spin,
or move the subscription to another queue. Any acquired permit MUST be released when
the handshake fails or the connection ends.

Pre-upgrade failures use an `application/json` body of exactly this semantic shape:

```json
{"error":{"code":"market_data_overloaded"}}
```

| Condition | HTTP status | Stable error code | Receiver or sequence effect |
|---|---:|---|---|
| Successful barrier and upgrade | 101 | none | One receiver; initial snapshot does not advance sequence |
| Missing/incomplete WebSocket upgrade | 426 | `upgrade_required` | None |
| Missing, duplicate, or unsupported subprotocol offer | 400 | `unsupported_subprotocol` | None |
| Missing/duplicate/unknown query key, empty or malformed symbol encoding, request body, or malformed handshake value | 400 | `malformed_request` | None |
| Unknown symbol resolved at the barrier | 404 | `unknown_symbol` | None |
| Market-data connection permits exhausted | 503 | `market_data_overloaded` | None |
| Engine queue full | 503 | `ingress_overloaded` | None |
| Draining, closed queue, or unavailable engine | 503 | `service_unavailable` | None |
| Known route with unsupported method | 405 | `method_not_allowed` | None |

An otherwise valid missing-upgrade response SHOULD include `Upgrade: websocket`.
Existing M3 route and total TCP-connection limits remain in force. If a TCP connection
is rejected before HTTP parsing under that existing limit, no HTTP response is promised.

A failed request MUST create no lasting receiver and consume no market-data sequence.
If a peer disappears after the subscription barrier has been admitted, the barrier MAY
complete in queue order; the returned receiver is then dropped without retry or sequence
effect.

## 5. Stream identity and sequence contract

At each fresh process start, the service MUST generate one new UUID-format `stream_id`.
The same value applies to every symbol for that process lifetime. Startup MUST fail
rather than knowingly reuse a prior value when generation fails. The stream ID is
market-data transport metadata; it MUST NOT enter or change the deterministic M2 event
tape.

Each configured symbol owns an independent `u64` market-data counter:

- the counter starts at zero on each fresh process;
- each live `trade`, `bbo`, or update `l2_snapshot` consumes exactly the next value;
- live values increase by exactly one in engine publication order, even when no receiver
  exists or a ring send reports zero receivers;
- traffic for one symbol never advances another symbol's counter;
- an initial snapshot reports the current value without advancing it; and
- after an initial snapshot at `S`, the first live frame on that connection, if any,
  MUST be `S + 1`.

Sequence addition MUST be checked. Exhaustion MUST stop new admission and initiate
abnormal shutdown; wraparound is prohibited.

Every market-data frame carries `version`, `stream_id`, `symbol`, and `sequence`.
Continuity is scoped by the pair `(stream_id, symbol)`, not by connection, command
index, event type, or process-global order. A client MUST treat any changed stream ID,
changed symbol, nonconsecutive live sequence, duplicate live sequence, transport loss,
or server close as loss of continuity.

`sequence` is a JSON `u64` integer. Clients whose numeric runtime cannot exactly
represent every `u64` MUST parse and compare it with an exact integer representation.

## 6. Initial snapshot and subscribe barrier

`Subscribe(symbol)` MUST execute on the engine queue after every earlier queued item
and before every later queued item. Within that one owner-thread operation, the engine
MUST:

1. capture the current sequence and authoritative configured-depth L2 projection;
2. create a receiver positioned before any later publication; and
3. return both to the connection task.

The first application frame on a successful connection MUST be the returned
`l2_snapshot` with `reason: "initial"`. No live frame may precede it. The snapshot
covers every earlier queue item; the receiver covers every later live item. Commands
that publish no visible item require no placeholder frame.

The initial snapshot replaces the client's prior L2 state. Its best bid and ask, if
present, also establish the initial BBO. M4 does not send a separate initial BBO. Empty
and one-sided books use empty arrays and absent sides derivable from those arrays; they
never invent prices or quantities.

## 7. Text-frame schemas

Each market-data record MUST occupy one complete UTF-8 JSON WebSocket text message.
Object-key order and insignificant whitespace are not compatibility surfaces. Field
names, typed values, enum strings, and array order are compatibility surfaces. The
server MUST NOT batch multiple records into one frame. `version` MUST be the JSON
integer `1`, and `type` MUST be exactly `"trade"`, `"bbo"`, or `"l2_snapshot"` as
defined below.

### 7.1 L2 snapshot

```json
{
  "version": 1,
  "type": "l2_snapshot",
  "reason": "initial",
  "stream_id": "6ba7b810-9dad-4c2c-8f3a-4f7692b44f58",
  "symbol": "BTC-USD",
  "sequence": 40,
  "depth": 20,
  "bids": [{"price_ticks": 10025, "quantity": "10"}],
  "asks": [{"price_ticks": 10030, "quantity": "7"}]
}
```

`reason` is exactly `"initial"` for the first frame and `"update"` for a live
snapshot. An update consumes a sequence; an initial snapshot does not. `depth` is the
configured maximum number of price levels per side. Bids are ordered highest price
first and asks lowest price first. Each side contains at most `depth` entries and no
duplicate price.

Each level quantity is the aggregate live remainder at that price. It is an unsigned
base-10 string representing a `u128`, so a legal aggregate greater than `u64::MAX`
remains exact for common JSON clients. Every quantity is positive. Prices remain exact
M1/M3 `i64` ticks, including negative, zero, and extreme values. Order IDs, owner IDs,
FIFO positions, and state below configured depth are absent.

A snapshot is complete and authoritative only for the displayed configured-depth
projection at its queue/command boundary. It is not the order-by-order, unlimited-size
[`GET /book`](../HTTP.md) representation.

### 7.2 Trade tick

```json
{
  "version": 1,
  "type": "trade",
  "stream_id": "6ba7b810-9dad-4c2c-8f3a-4f7692b44f58",
  "symbol": "BTC-USD",
  "sequence": 41,
  "price_ticks": 10030,
  "quantity": 2
}
```

Exactly one tick MUST be emitted for each M2 `trade_executed`, in exact M2 effect
order. `price_ticks` and `quantity` MUST equal that event and retain their `i64` and
`u64` meanings. A tick MUST NOT expose maker/taker order IDs or owner IDs. Its sequence
is its unique identity within `(stream_id, symbol)`; M4 promises neither a separate
trade ID nor replay after loss.

### 7.3 BBO update

```json
{
  "version": 1,
  "type": "bbo",
  "stream_id": "6ba7b810-9dad-4c2c-8f3a-4f7692b44f58",
  "symbol": "BTC-USD",
  "sequence": 42,
  "bid": {"price_ticks": 10025, "quantity": "10"},
  "ask": null
}
```

`bid` and `ask` are either `null` or the best aggregate level, using the same level
schema and `u128` quantity string as L2. A command emits exactly one BBO update if and
only if its final BBO differs in price or aggregate quantity from the prior final BBO.
Only final command-boundary state is visible; transient intra-command best prices are
never published.

When a command emits trade, BBO, and L2 records, their consecutive sequence values and
frame order MUST follow section 3. The BBO and following L2 MUST describe the same final
post-command state.

## 8. Bounded resources and slow consumers

M4 MUST add finite startup configuration with these defaults and constraints. Exact CLI
flag spelling may differ, but resolved values and meanings are public operational
contract and MUST be emitted in startup/shutdown evidence.

| Setting | Default | Required bound or meaning |
|---|---:|---|
| L2 depth | 20 | Integer `1..=100`; maximum levels per side |
| Market-data ring capacity | 1024 | Power of two and at least 64; retained events per symbol |
| Market-data connections | 128 | Positive and no greater than M3 total connection limit |
| WebSocket write timeout | 1 second | Finite positive deadline for each send/flush attempt |
| WebSocket close timeout | 1 second | Finite positive graceful-close deadline |
| Ping interval | 15 seconds | Finite positive heartbeat interval |
| Pong timeout | 30 seconds | Finite peer-liveness deadline greater than ping interval |
| Maximum write buffer | 64 KiB | Explicit hard library limit; an unlimited default is forbidden |
| Maximum inbound message | 1 KiB | Hard reassembled application-message limit |

The maximum possible encoded outbound frame for the configured symbols and depth MUST
fit within the configured write-buffer limit, validated at startup. WebSocket
compression MUST remain disabled.

There MUST be exactly one fixed-capacity broadcast ring per configured symbol. It stores
each immutable event once regardless of subscriber count. Capacity MUST be a power of
two and MUST be at least 64 so the effective Tokio ring size equals the advertised
size and an ordinarily prompt reader can receive a normal three-record match
publication without a false lag disconnect. Publication MUST be
non-waiting and MUST NOT retry, sleep, block on capacity, write a socket, or iterate over
subscribers.

Each upgraded socket MUST be owned by one async connection task with one receiver
cursor. The only connection-attributable application buffering is that cursor, at most
one currently processed immutable event, the bounded inbound message, and the explicitly
bounded WebSocket write buffer. There is no per-client application queue, global
unbounded publisher queue, or sink registry held behind a fanout lock.

On the first receiver lag indication, the connection is permanently invalid:

1. no later application frame may be sent on that socket;
2. the task MUST record the missed count reported by the ring;
3. it MUST make at most one deadline-bounded best-effort close attempt with code `1013`
   (`Try Again Later`) and reason `resync_required`; then
4. it MUST drop the socket and release all connection-specific state.

The task MUST NOT skip to the oldest retained event and continue. A send/flush timeout,
full WebSocket write buffer, serialization failure, invalid internal sequence, peer I/O
failure, or missed pong also terminates only that connection. Close delivery is best
effort and is not required before resources are released.

Client text or binary application messages at or below the inbound limit are unsupported
and MUST close with code `1008` (`Policy Violation`). Oversized messages MUST be rejected
without unbounded accumulation. Ping, pong, and close control frames MUST be handled.
A successful send or flush means only that the server-side stack accepted bytes; it does
not prove peer consumption.

## 9. Gap detection and resynchronisation

The normative client state machine is:

1. Open a new connection for one symbol using the required v1 subprotocol.
2. Accept only an initial L2 snapshot as the first application frame. Replace all prior
   local L2/BBO state and set `(stream_id, symbol, last_sequence)` from it.
3. For every live frame, require the same stream ID and symbol and require
   `sequence == last_sequence + 1` using checked exact-integer arithmetic.
4. Apply the record only after those checks, then advance `last_sequence`. An update
   L2 snapshot replaces the visible L2 projection; it is not a delta.
5. On mismatch, duplicate, decode failure, close, or transport loss, mark the local
   feed invalid and reconnect with bounded randomized backoff.
6. Replace local state only from the next connection's initial snapshot. Do not request
   or expect replay.

The server MUST NOT repair a lagged connection in place. There is no in-band resync
message, resume token, replay offset, or buffered recovery mode in M4.

The resynchronisation boundary is the fresh queue-ordered initial snapshot. It captures
the current top-N state after every command before its barrier, including the net state
of commands missed by the old connection; its receiver then supplies later live items.
It does not reproduce lost trade ticks. A consumer requiring every trade MUST regard any
gap as irrecoverable historical loss under M4.

## 10. Shutdown and abnormal failure

Graceful shutdown MUST preserve M3's admitted-work ownership and use this order:

1. mark the service draining, stop accepting TCP connections and new HTTP/WebSocket
   work, and return `service_unavailable` for pre-admission work where a response remains
   possible;
2. close the M3 sender and drain all already admitted commands, snapshots, and
   subscription barriers in FIFO order, continuing normal market-data publication for
   admitted commands;
3. after the owner queue is empty, drop every per-symbol publisher;
4. let connection tasks attempt to flush already retained frames and then send close
   code `1001` (`Going Away`) within their finite write/close deadlines;
5. abort any connection task that cannot complete within the finite egress bound, so a
   slow or non-reading peer cannot delay shutdown indefinitely; and
6. join the engine, HTTP tasks, and WebSocket tasks, emit reconciled final counters, and
   exit.

Frames delivered before termination MUST remain well formed, symbol-correct, and ordered.
No application frame may follow a server terminal close boundary. Graceful shutdown is a
terminal continuity loss, not an ordinary gap that can be repaired against the stopping
process.

An engine panic or unexpected owner exit MUST close admission and publishers and
terminate sockets with a best-effort `1011` (`Internal Error`). The process MUST NOT
create a replacement empty engine. `SIGKILL`, process abort, allocation failure, power
loss, and durable recovery before M9 remain outside graceful guarantees.

## 11. Required invariants

The implementation and independent validation MUST demonstrate:

1. **Single authority:** only the engine owner reads mutable books for publication,
   advances sequence, updates projections, or creates subscription receivers.
2. **M2 preservation:** the same ordered commands produce identical M2 events and final
   books with M4 enabled or disabled; network timing cannot change matching.
3. **Projection parity:** every tick equals its M2 fill and every BBO/L2 record equals
   independent aggregation of the authoritative post-command book.
4. **Publication order:** M2-order trades precede final BBO, which precedes final L2,
   before the command's HTTP completion publication.
5. **Sequence continuity:** live frames are exactly consecutive within
   `(stream_id, symbol)`; initial snapshots establish but do not advance the position.
6. **Symbol isolation:** traffic, lag, close, or recovery for one symbol cannot advance,
   leak into, or stall another symbol.
7. **Race-free subscription:** the initial snapshot includes every earlier queue item
   and the receiver includes every later published item, without duplicate boundary data.
8. **Finite memory:** rings, connection counts, snapshot depth, inbound messages, write
   buffers, and all socket deadlines are finite; no alternate unbounded queue exists.
9. **Slow-reader isolation:** a stalled connection cannot delay matching, HTTP
   completion, a healthy subscriber, or shutdown beyond the documented finite bound.
10. **Terminal lag:** a receiver that loses one or more retained items is disconnected
    and observes no later application data on that socket.
11. **Restart visibility:** every fresh process uses a different stream ID and starts
    independent symbol counters at zero.
12. **Drain ordering:** every admitted command publishes before publishers close; slow
    WebSocket tasks cannot prevent process exit.
13. **No private leakage:** market-data frames contain no owner or maker/taker order ID.
14. **Read-only transport:** WebSocket input cannot submit, cancel, retry, or mutate an
    order.

## 12. Observability contract

M4 MUST expose or log process-lifetime counters/gauges sufficient to reconcile tests
and measurements:

- WebSocket upgrade attempts and outcomes by stable status/error code;
- current, high-water, and rejected market-data connections;
- current/high-water subscribers per configured symbol;
- subscription barriers admitted, completed, and rejected;
- current sequence per symbol and logical events generated by type;
- ring sends with receivers and logical events published with no receiver;
- frames and bytes successfully written by type;
- lag disconnects and total missed count reported by lag notifications;
- write-timeout, write-buffer-full, serialization, protocol, peer-I/O, heartbeat,
  shutdown, and abnormal-engine disconnects;
- graceful versus abnormal publisher/engine exit and forced task aborts; and
- resolved configuration, effective ring capacity, and maximum encoded frame size.

Disconnect logs SHOULD include connection ID, symbol, stream ID, last delivered
sequence, current source sequence, reason, and missed count when known. Unbounded values
such as connection IDs and stream IDs MUST NOT become metric labels. Metrics MUST NOT
change engine ordering, add wall-clock fields to M2 events, or claim peer consumption
from a successful socket write.

Because one logical event fans out, shutdown reconciliation MUST distinguish logical
events from per-connection delivery attempts.

## 13. Exact M4 scenario bindings

The independent [M4 scenario inventory](../scenarios/M4.md) uses IDs `L1`–`L4`, `O1`–`O5`, `C1`–`C3`,
`G1`–`G5`, `S1`–`S5`, `D1`–`D3`, `F1`–`F4`, `M1`–`M3`, `T1`–`T4`, and
prohibitions `N1`–`N9`. M4 implementation evidence MUST cite these exact IDs.

| Contract area | Bound scenarios |
|---|---|
| One-symbol subscription, initial snapshot, empty/live lifecycle | `L1`, `L2`, `L3`, `D2` |
| Connection replacement as the only selection change | `L4`, `O3`, `D1`, `D3` |
| Shared cross-type ordering and contiguous successor rule | `O1`, `O2`, `O4`, `O5`, `C3`, `N2` |
| L2 completeness and BBO coherence | `C1`, `C2`, `N4` |
| Gap detection and reconnect snapshot boundary | `G1`, `G2`, `G3`, `G4`, `S2`, `S3`, `N1`, `N6` |
| Slow-consumer bounds and healthy-client isolation | `S1`, `S4`, `S5`, `D1`, `T3`, `N5` |
| Malformed/unsupported input and bounded rejection | `F1`, `F2`, `F3`, `F4`, `N7` |
| Per-symbol isolation and recovery | `G5`, `M1`, `M2`, `M3`, `N3` |
| Orderly stop, restart epoch, and stale-session exclusion | `T1`, `T2`, `T3`, `T4`, `N8`, `N9` |

Where the scenario prose describes adding/removing symbols or one logical client
selecting both symbols (`L4`, `M2`), v1 binds that behavior to separate one-symbol
connections: open the new symbol connection and accept its initial snapshot, then close
the old connection. A connection never changes selection in place.

Where it describes malformed, duplicate, conflicting, or resync controls (`F1`, `F3`),
v1 binds pre-upgrade selection errors to the HTTP table in section 4 and any post-upgrade
text/binary application message to terminal code `1008`. There is no valid in-band
control to duplicate.

Where multi-symbol gap scenarios describe one client (`G5`, `M3`), they use independent
connections and independent `(stream_id, symbol)` sequence cursors. Only the affected
connection reconnects. Where recovery expects changes made during the gap (`G2`), the
new initial L2 snapshot includes their current net book effect; lost trades are not
replayed.

## 14. Release-validation evidence

An M4 implementation release is incomplete without actual evidence for one
reviewed commit. It MUST include:

- client-visible transcripts for every exact scenario in section 13, including upgrade
  boundaries, decoded frames, stream ID, symbol, sequence, initial/reconnect boundaries,
  close/error outcome, and configured finite limits;
- independently known authoritative book state for `C1`–`C3`, and controlled omission
  plus recovered-baseline evidence for `G1`–`G5`;
- deterministic tests covering empty/nonempty initial snapshots at sequence zero and
  nonzero, one-/two-sided books, all `i64` tick boundaries, `u64::MAX` quantities, and
  a same-level L2 aggregate greater than `u64::MAX`;
- exact trade/BBO/L2 ordering for partial fill, multi-level sweep, same-price makers,
  cancellation, self-trade-prevention cancellation and continuation, market remainder,
  rejected commands, and below-depth-only mutation;
- two-symbol interleaving and subscription barriers placed before, between, and after
  commands, proving independent sequences and no snapshot/live race;
- a fixed command tape run twice with an injected fixed stream ID, producing
  byte-identical market-data frames while preserving the existing M2 golden tape;
- property tests comparing every cached/emitted top-N projection with independent
  aggregation of the authoritative book after generated command prefixes;
- real HTTP/1.1 upgrade tests for every query, upgrade, subprotocol, saturation, and
  admission mapping in section 4;
- deterministic ring-overflow and independently stalled-writer tests proving terminal
  lag/write bounds without timing sleeps as the primary oracle;
- repeated slow-client connect/drop evidence showing stable ring, retained-value,
  connection, task, and memory high-water bounds while healthy subscribers remain
  contiguous;
- lifecycle fault evidence for peer reset, invalid input, serialization failure,
  engine exit, and shutdown with admitted work plus a stalled socket; and
- the repository's ordinary formatting, lint, test, documentation-link, and whitespace
  checks with actual output.

M4 MUST rerun the unchanged M3 500-offered-RPS release protocol and report comparison
evidence for no subscribers, fast subscribers, configured-maximum subscribers, mixed
fast/stalled subscribers, and adversarial deep-level aggregation. Correctness and
boundedness are gates. Benchmark results are evidence, not a new capacity claim; M4
MUST NOT revise the historical M3 gate after seeing its results. A material engine or
HTTP p99 regression requires profiling and review rather than an unsupported benchmark
claim.

## 15. Explicit non-goals

M4 MUST NOT add or claim:

- durable retention, historical trade replay, exactly-once delivery, resume tokens, or
  sequence continuity across process restarts;
- L2 deltas, unlimited depth, order-by-order/L3 market data, owner identity, or a
  guarantee about state below configured depth;
- multi-symbol connections, runtime subscribe/unsubscribe, wildcard feeds, or per-client
  filters beyond one symbol;
- order entry/cancel over WebSocket, authentication, authorization, entitlements,
  client rate limits, TLS, HTTP/2, or public-internet hardening;
- Kafka, Redis, NATS, a database, journal, persistence, recovery snapshot, sidecar,
  another process, container, Kubernetes resource, load balancer, or service mesh;
- per-symbol engine threads, sharding, shared-book locks, busy spinning, thread pinning,
  or an unmeasured lock-free ring;
- binary framing, WebSocket compression, schema registry, or generated SDK;
- M5 timestamps, simulator behavior, or later PRD throughput claims; or
- changes to M1 matching, price-time priority, self-trade prevention, M2 event meanings,
  M3 status mappings, or the full `GET /book` response.

The concrete WebSocket crate, Hyper upgrade adapter, and lazy-serialization mechanism
remain implementation choices only if they preserve every observable rule and bound
above. L2 deltas, in-band resync, multi-symbol connections, durable replay, or continuity
across restart require a later written protocol decision and are not inferred into v1.
