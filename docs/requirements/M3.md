# M3 HTTP ingestion architecture and normative requirement

**Status:** complete; no unresolved M3 captain decision  
**Requirement author:** Codex, M3 architecture scout  
**Date:** 2026-09-16  
**Scope:** M3 only — a co-located HTTP boundary over the deterministic M2 engine

## 1. Purpose and authority

This report is the written architecture and behavioral requirement for M3. A separate
scenario author should derive prose scenarios from it before reading production code,
and a separate implementer should build against those scenarios. The normative words
**MUST**, **MUST NOT**, **SHOULD**, and **MAY** have their usual requirements meanings.

This report incorporates and is subordinate to:

- `docs/ROADMAP.md`: M3 adds only `POST /orders`, `DELETE /orders/:id`, and
  `GET /book`, with a bounded channel and immediate overload rejection;
- `docs/DELIVERY.md`: written requirements and independently authored scenarios
  precede implementation, and the three delivery roles remain separate;
- `docs/BENCHMARK.md` and the captain's benchmark decision: the provisional gate is
  500 offered order-command HTTP requests per second, co-located, with client-observed
  HTTP-wall p90 at or below one second;
- ADR-0002 and ADR-0004: the existing safe order book and exact integer ticks remain
  authoritative;
- ADR-0003: exactly one thread owns and writes every book, reached through a bounded
  channel;
- ADR-0006: the server and engine remain one process with no infrastructure; and
- ADR-0007: symbols remain isolated books behind the one engine writer.

The completed M1 and M2 architecture reports define matching, cancellation, domain
errors, ordered engine events, and deterministic execution. M3 is an adapter around
that engine; it MUST NOT reproduce or alter matching logic.

The captain has now settled the inherited self-trade-prevention rule: when the next
maker belongs to the incoming order's owner, cancel that encountered resting maker,
continue matching the incoming remainder, and retain all earlier third-party fills.
M3 consumes that settled M1/M2 behavior as described in section 8. It does not choose
a second policy or create a transport-only substitute for the M2 event/result shape.

## 2. Required outcome

M3 MUST ship one Rust server process that:

1. exposes `POST /orders`, `DELETE /orders/:id`, and `GET /book` over HTTP;
2. converts valid HTTP input to the existing typed M2 engine boundary;
3. sends commands and snapshot queries to the one engine owner through one bounded
   in-process queue;
4. uses non-waiting admission and returns an immediate overload response when bounded
   capacity is unavailable;
5. returns an order-command response only after that command has fully completed in
   the engine, except when the client connection disappears;
6. returns a snapshot taken atomically by the engine owner at a defined point in the
   same total order as commands;
7. shuts down without retracting or silently abandoning work already admitted to the
   engine queue during a graceful shutdown; and
8. produces the HTTP-wall and overload evidence specified in section 13.

M3 is not a durable or exactly-once service. A process crash can lose all in-memory
state, and a client that loses its connection after admission can be uncertain whether
the command took effect. Persistence and recovery remain M6/M9 work.

## 3. Architecture and ownership

The server has four conceptual components:

1. **HTTP adapter.** Routes requests, enforces finite request/body limits, decodes the
   strict wire schema, and maps typed results to HTTP.
2. **Bounded ingress queue.** A finite multi-producer/single-consumer channel. Each
   message owns either one typed engine command or one snapshot query and a one-shot
   completion sender.
3. **Engine thread.** The sole owner of the M2 engine and all books. It receives queue
   messages one at a time and completes each message before receiving the next.
4. **Response adapter.** Awaits the one-shot completion and serializes the detached
   typed result. It never reads or mutates a live book.

The conceptual ingress type is:

```rust
enum Ingress {
    Command {
        command: EngineCommand,
        completion: OneShotSender<NonEmptyEventBatch>,
    },
    Snapshot {
        symbol: Symbol,
        completion: OneShotSender<Result<BookSnapshot, CommandError>>,
    },
}
```

Exact Rust names may differ, but the ownership may not. The book MUST NOT be placed
behind `Arc<Mutex<_>>`, `RwLock`, a concurrent map, or any shared mutation primitive.
HTTP tasks MUST NOT call M1 book operations directly. The engine thread MUST perform no
HTTP parsing, socket I/O, or JSON serialization.

The queue capacity MUST be a finite positive startup configuration and MUST remain
fixed for the process lifetime. The HTTP layer MUST also impose a finite positive
in-flight-request limit and a finite body limit; it MUST NOT hide an unbounded
application queue in front of the bounded engine queue. The selected limits and all
defaults MUST be documented, and benchmark evidence MUST record their actual values.
These numeric values are engineering configuration, not a captain policy decision.

## 4. Admission, ordering, and completion ownership

### 4.1 Non-waiting bounded admission

For a recognized endpoint, the adapter MUST acquire any application admission permit
without waiting. Once it has a typed engine request, it MUST attempt queue insertion
exactly once with a non-waiting operation equivalent to `try_send`.

- If insertion succeeds, the request is **admitted**.
- If the queue is full, admission MUST return `503 Service Unavailable` immediately.
  It MUST NOT await capacity, retry internally, spin, or move the command to another
  queue.
- If the queue is closed, the engine is unavailable, or graceful draining has begun,
  the request MUST return `503 Service Unavailable` and MUST NOT mutate a book.
- Failure to obtain the finite HTTP admission permit MUST use the same immediate 503
  behavior.

“Immediately” is a control-flow property: the overload path performs no wait for
future engine capacity. It is not an invented millisecond threshold. A conformance
test MUST hold the engine paused, fill the queue, and prove that the next request
receives its 503 while the engine remains paused.

The HTTP request-body limit MUST be at most 16 KiB for M3. A streaming decoder MUST
stop accumulating once the configured limit is exceeded. Each body is therefore
bounded even before engine admission.

### 4.2 Total order

The authoritative live command order is successful insertion order as observed by the
single queue consumer. The engine assigns the next monotonic M2 command index when it
dequeues a command, starting at one for each fresh process. A request rejected before
queue insertion receives no command index and has no engine effect.

Two concurrent HTTP requests have no ordering guarantee based on socket acceptance,
header arrival, client timestamp, or handler scheduling. Whichever is admitted first is
first in engine order. Given the resulting ordered typed command sequence, M2
determinism still applies; M3 does not claim that two concurrent network runs induce
the same order.

Snapshot queries share the same queue. They act as barriers but do not consume an M2
command index. A snapshot observes all commands dequeued before it and none dequeued
after it.

### 4.3 Completion ownership and client cancellation

After admission, the queue message—not the HTTP task—owns the command. The engine MUST
execute it exactly once in queue order even if the HTTP request future is cancelled,
the peer disconnects, or the response receiver is dropped. Failure to deliver the
one-shot result after execution is ignored as a transport loss; it MUST NOT roll back,
retry, or stop the engine.

An attached HTTP handler MUST await the one-shot result and send no success response
until the engine has completed the full event batch. M3 MUST NOT acknowledge with
`202 Accepted`, acknowledge on queue insertion, or run an admitted command a second
time after a response-write failure.

M3 MUST NOT impose a server-side processing timeout after successful queue insertion.
Such a timeout would turn a still-executing command into an ambiguous result. Client or
load-generator timeouts may close the connection, but they do not cancel the command.
There is no automatic retry or idempotency-key feature in M3.

## 5. Common HTTP wire rules

The server MUST listen on a configured address in one process and MUST support HTTP/1.1
keep-alive. TLS, HTTP/2, proxies, and external gateways are outside M3.

All request and response bodies defined here are UTF-8 JSON. Requests with a body MUST
use `Content-Type: application/json`; parameters such as `charset=utf-8` MAY be
accepted. JSON bodies MUST be objects, MUST contain every required field exactly once,
and MUST reject unknown fields. Unknown variants, missing fields, duplicate object
keys, trailing non-whitespace data, non-integral numeric syntax for integer fields, or
values outside their declared range are malformed requests.

Wire scalar meanings match M2:

- `symbol` is a nonempty string, with no trimming, case folding, or Unicode
  normalization;
- `order_id` and `owner_id` are JSON integers in `0..=u64::MAX`;
- `side` is exactly `"buy"` or `"sell"`;
- `price_ticks` is a JSON integer in `i64::MIN..=i64::MAX`; and
- `quantity` is a JSON integer in `0..=u64::MAX`.

M3 deliberately exposes ticks by the explicit field name `price_ticks`. It performs no
floating-point conversion and needs no instrument tick-size catalog. A future human
decimal API would require a separate instrument-metadata contract; it is not silently
introduced here.

Every JSON response MUST declare `Content-Type: application/json`. HTTP JSON whitespace
and object-key order are not byte-compatibility surfaces. Typed values, array order,
status, and error codes are compatibility surfaces.

## 6. Endpoint contracts

### 6.1 `POST /orders`

The endpoint accepts exactly one limit or market order.

Limit body:

```json
{"type":"limit","symbol":"BTC-USD","order_id":1,"owner_id":7,"side":"buy","price_ticks":10025,"quantity":10}
```

Market body:

```json
{"type":"market","symbol":"BTC-USD","order_id":2,"owner_id":8,"side":"sell","quantity":4}
```

Zero quantity is structurally valid and MUST reach the engine so M2 returns its typed
`invalid_quantity` rejection. All `i64` tick values are valid. The HTTP adapter MUST
not reimplement unknown-symbol, live-ID collision, liquidity, matching, or self-trade
logic.

For an engine completion, the response body is:

```json
{"events":[/* the ordered M2 event batch for this command */]}
```

The event objects MUST preserve the amended M2 typed event meanings and order: zero or
more execution/state events followed by exactly one terminal completion or rejection.
The adapter MUST NOT sort, omit, combine, or infer engine events.

### 6.2 `DELETE /orders/:id?symbol=:symbol`

The path `id` is an unsigned base-10 integer in `0..=u64::MAX` with no sign. Because
M1/M2 order identity is symbol-scoped and the same ID may be live on two symbols, the
`symbol` query parameter is REQUIRED and MUST occur exactly once. A request without it
is malformed rather than a search across books.

Example:

```text
DELETE /orders/1?symbol=BTC-USD
```

The adapter constructs the existing M2 cancel command. It adds no owner credential and
does no authentication or authorization. A successful cancel returns the same ordered
event-batch envelope as `POST /orders`. An unknown, filled, already cancelled, or
wrong-symbol order maps from M2's `order_not_found` rejection as specified in section 7.

### 6.3 `GET /book?symbol=:symbol`

The `symbol` query parameter is REQUIRED exactly once. The endpoint takes no body. It
enqueues a snapshot query on the same bounded queue and returns the detached M1
snapshot captured by the engine thread.

The response shape is:

```json
{
  "symbol":"BTC-USD",
  "bids":[
    {"price_ticks":10025,"orders":[
      {"order_id":1,"owner_id":7,"remaining":10}
    ]}
  ],
  "asks":[]
}
```

Bids MUST be ordered from highest to lowest price; asks from lowest to highest. Orders
within a level MUST be ordered oldest to newest. Every returned order has positive
`remaining`; the level price and side are represented by containment and MUST agree
with the engine snapshot. Empty sides are empty arrays. The endpoint MUST NOT return a
partially copied snapshot or hold a reference into live engine state.

This is an on-demand query, not an M4 market-data protocol. It carries no subscriber
sequence, BBO stream, incremental update, resynchronization mechanism, or slow-consumer
buffer.

## 7. Deterministic HTTP status and error mapping

M3 selects `503 Service Unavailable` for bounded-capacity rejection. This is a server
capacity/unavailability condition, not client-specific rate limiting, so `429` is not
used. The roadmap explicitly leaves this status for M3 to decide.

Successful engine commands use `200 OK`, including a limit that rests, an order that
fully fills, an unfilled market remainder, a successful cancel, and a command that
encounters self-trade prevention but completes under the settled rule. M3 does not use
`201` because an accepted order need not create a resting resource.

The complete mapping is:

| Condition | Status | Stable error code | Engine mutation |
|---|---:|---|---|
| Engine command completed | 200 | none | Exactly the M2 result |
| Snapshot completed | 200 | none | None |
| M2 `unknown_symbol` | 404 | `unknown_symbol` | None |
| M2 `order_not_found` | 404 | `order_not_found` | None |
| M2 `duplicate_order_id` | 409 | `duplicate_order_id` | None |
| M2 `invalid_quantity` | 422 | `invalid_quantity` | None |
| Queue/admission full | 503 | `ingress_overloaded` | None |
| Draining, queue closed, or engine unavailable before admission | 503 | `service_unavailable` | None |
| Body exceeds limit | 413 | `body_too_large` | None |
| Unsupported request content type | 415 | `unsupported_media_type` | None |
| Malformed path/query/JSON/wire value | 400 | `malformed_request` | None |
| Known path with unsupported method | 405 | `method_not_allowed` | None |
| Unknown route | 404 | `route_not_found` | None |
| Completion channel disappears unexpectedly after admission | 500 | `completion_unavailable` | Unknown to client; process begins shutdown |

A pre-engine error body is exactly the semantic shape:

```json
{"error":{"code":"ingress_overloaded"}}
```

For a typed M2 domain rejection, the body MUST retain the event batch and add the same
stable code:

```json
{"events":[/* one M2 command_rejected event */],"error":{"code":"duplicate_order_id"}}
```

Human-readable text MAY be logged but is not an HTTP compatibility field. Route/method
selection occurs first; finite application admission occurs before body accumulation;
wire validation occurs before queue insertion; M2 domain validation occurs only after
insertion. Consequently an otherwise malformed recognized request may receive 503 if
the finite HTTP admission limit is already exhausted, while a parsed request never
mutates state unless queue admission succeeds.

## 8. Settled self-trade behavior at the boundary

M3 MUST rely on the engine to apply this sequence when an incoming order reaches a
same-owner maker under price-time priority:

1. preserve every earlier third-party fill and its existing ordered trade event;
2. cancel the encountered same-owner maker's entire live remainder;
3. emit the explicit M1/M2 state/event representation for that maker cancellation;
4. continue matching the unchanged incoming remainder against the next eligible maker;
5. repeat the rule for each later encountered same-owner maker; and
6. finish with the normal incoming-order disposition (filled, resting, or unfilled).

No trade may have equal maker and taker owners. The HTTP response is `200 OK` because
this is a successful prevention-and-continue result, not an input rejection. Its
ordered `events` array MUST make the retained third-party fills, each maker cancellation,
and final disposition observable exactly as the amended M2 engine batch defines them.

The earlier M1/M2 reports were written before the captain's decision and intentionally
left their exact result/event variant unresolved. Their normative schemas MUST be
amended before M1/M2/M3 implementation freezes a v1 event schema. This M3 report does
not invent a competing HTTP-only cancellation event, disguise the maker cancellation
as `order_not_found`, or drop it from the response. The schema amendment is requirement
maintenance following a settled decision, not a remaining captain call.

## 9. Snapshot consistency and serialization safety

The snapshot operation is linearizable at the point the engine thread handles its queue
message. The engine MUST finish the prior message, create the complete detached
snapshot without interleaving another message, and only then handle the next message.

JSON serialization MAY occur on an HTTP/runtime thread after detachment. A slow client
therefore cannot block matching after snapshot capture, and later commands cannot
change the detached value being serialized. Snapshot creation itself runs on the engine
thread and SHOULD remain a direct bounded copy of current book state; M3 MUST NOT add a
snapshot cache, replica, background refresher, or eventually consistent shared view.

If queue/admission capacity is unavailable, `GET /book` receives the same immediate 503
rather than bypassing the writer. An unknown symbol is resolved by the engine at the
snapshot's queue position and returns 404.

## 10. Shutdown and failure safety

Graceful shutdown MUST use this order:

1. mark the service not ready/draining and stop accepting new connections;
2. make every request not yet admitted fail without book mutation, using 503 where an
   HTTP response can still be sent;
3. prevent new queue senders, then close the final sender;
4. let the engine drain every already-admitted command and snapshot in FIFO order,
   attempting every one-shot completion;
5. let attached handlers write their completed responses and close keep-alive
   connections; then
6. join the engine thread and exit.

A graceful shutdown MUST NOT cancel, reorder, or retry an admitted command. If the
client has already gone away, the engine still completes the command and merely loses
the response. A configured operational hard-stop deadline MAY terminate the process,
but documentation and tests MUST not describe such termination as graceful or lossless.

If the engine thread panics, exits unexpectedly, or drops a completion sender, the HTTP
side MUST stop admitting work and begin shutdown. A waiting client receives 500 if the
connection remains usable; its command outcome is explicitly uncertain. The server
MUST NOT create a replacement empty engine inside the same process and continue as if
state were intact.

SIGKILL, power loss, process abort, allocation failure, and machine failure are outside
M3's safety guarantee. With no journal or persistence, restart begins from the configured
empty books.

## 11. Invariants and acceptance properties

The implementation and scenarios MUST demonstrate:

1. **Single ownership:** only the engine thread mutates or snapshots books.
2. **Boundedness:** queue, in-flight request count, and request bodies have finite
   configured bounds; no alternate unbounded application queue exists.
3. **Immediate overload:** a full/closed queue never waits for future capacity and
   never mutates state for the rejected request.
4. **One admission, one execution:** each successfully enqueued command is executed
   once; each pre-admission failure is executed zero times.
5. **Completion truth:** a 200 order response implies the returned complete M2 batch
   has already been applied; no response is an insertion-only acknowledgment.
6. **Disconnect independence:** cancelling a handler after admission does not cancel
   or repeat the command.
7. **Engine order:** commands run in dequeue order and their event arrays retain M2
   order.
8. **Snapshot linearizability:** a queued snapshot is exactly the state after all
   earlier messages and before all later messages.
9. **Domain parity:** direct M2 execution and HTTP execution of the same ordered typed
   commands yield equal event meanings and final snapshots.
10. **Status determinism:** every listed condition maps to the exact status and code in
    section 7 without inspecting error text.
11. **Self-trade safety:** same-owner makers are cancelled and matching continues;
    earlier third-party fills remain; no self-trade is emitted.
12. **Graceful drain:** all admitted work completes in FIFO order before graceful exit,
    including work whose HTTP receiver disappeared.

Required end-to-end coverage includes both order variants; resting, full-fill,
multi-maker, partial, and unfilled outcomes; successful and repeated cancel; every M2
domain rejection; malformed/oversized/wrong-media requests; two symbols with identical
order IDs; queue-full behavior with a paused engine; disconnect before and after queue
admission; shutdown with queued work; snapshots before, between, and after commands; and
the settled self-trade sequence with a third-party fill before and after an encountered
same-owner maker.

## 12. Observability required for honest evidence

M3 MUST expose or log process-lifetime counters sufficient to reconcile a benchmark:

- recognized HTTP requests by endpoint and status;
- commands admitted to the engine queue;
- commands completed and domain-rejected by reason;
- admission/queue overload rejections;
- current and high-water queue depth;
- snapshots admitted/completed/rejected;
- completion delivery failures caused by disconnected handlers; and
- graceful versus abnormal engine exit.

Counters MUST be read without mutating engine ordering and MUST NOT add wall-clock
timestamps to domain events. Per-stage order timestamps belong to M5. Debug request
logging SHOULD be disabled during the baseline and its setting recorded.

At the end of a run, offered requests MUST reconcile as completed HTTP responses,
client timeouts/connection failures, or still outstanding. Server admissions MUST
reconcile as engine completions/rejections plus work still executing at the measurement
cut; the harness MUST allow a documented drain before collecting final counters.

## 13. HTTP-wall benchmark protocol

### 13.1 Meaning of the provisional gate

The M3 starting gate is exactly:

- **offered load:** 500 `POST /orders` or `DELETE /orders/:id` attempts per second;
- **placement:** load generator and release server on the same physical host, using
  loopback; and
- **latency:** client-observed HTTP-wall p90 at or below one second.

RPS and QPS are aliases. `GET /book` does not count toward the 500 order-command rate.
The offered rate is not an assertion that every request is accepted. A run MUST report
rejections and accepted throughput and MUST NOT relabel offered RPS as successful RPS.

### 13.2 Reproducible baseline workload

The canonical M3 run MUST use a deterministic, dependency-safe mix across four
configured symbols, round-robin by scheduled request number:

- 50% `POST` non-crossing limit buys of quantity 1 at a documented low tick, with
  unique IDs;
- 25% `POST` market sells of quantity 1, each consuming one preloaded high-tick buy;
  and
- 25% `DELETE` commands targeting distinct preloaded low-tick buy IDs that the market
  orders cannot reach during the run.

Before timing, each fresh server MUST be preloaded outside the measured interval with
enough match-pool and cancel-pool orders for warm-up plus measurement plus at least 10%
margin. Prices MUST separate the pools so scheduled market orders cannot consume cancel
targets and new resting orders cannot displace the match pool. All baseline commands
are therefore expected to reach successful engine completions; any domain rejection is
reported as a fixture/harness defect, while 503 remains overload evidence.

This mix is an M3 comparison fixture, not a production-traffic claim. The evidence MUST
state exact symbols, ticks, IDs, preload counts, queue capacity, in-flight limit, body
limit, and final status counts.

### 13.3 Load generation and timing

For each of at least three fresh-process runs:

1. build and run the server in the release profile;
2. preload the documented fixture and verify a snapshot before timing;
3. warm up at 500 offered requests/second for 30 seconds;
4. immediately measure at 500 offered requests/second for 120 seconds;
5. stop offering new work, allow a documented drain, capture server counters and a
   final snapshot, then shut down gracefully; and
6. report every run separately plus an aggregate summary—never only the best run.

The generator MUST be open-loop: requests are scheduled from a monotonic clock at a
constant 2 ms interval independent of earlier response completion. It MUST have enough
bounded concurrency to continue scheduling while requests are outstanding, but MUST
not create its own unbounded queue. HTTP/1.1 keep-alive MUST be used with a fixed,
reported connection count and no proxy or TLS. The generator and server SHOULD use
disjoint CPU cores where the host permits; affinities and any inability to isolate them
MUST be reported.

For each request, record:

- scheduled time;
- actual dispatch time immediately before handing the request to the client transport;
- completion time after the entire response body is read, or timeout/failure time;
- endpoint, status, stable error code, and response-byte count.

The gate's **HTTP-wall latency** is `completion - dispatch`, including local connection
pooling, socket, server queue, engine execution, response serialization, and full body
read. Also report `dispatch - scheduled` as generator scheduling lag and
`completion - scheduled` as offered-load response time. This exposes a co-located
generator that cannot actually maintain the schedule instead of hiding its delay.

Use a client timeout greater than one second (ten seconds is the recommended M3 value)
and report timeouts separately. Percentiles MUST come from raw per-request samples or a
histogram with adequate precision, not averages or endpoint-side timings. Report p50,
p90, p95, p99, and max for:

1. all completed order-command HTTP requests;
2. 200 engine-completed requests;
3. 503 overload responses; and
4. each endpoint/mix category.

The provisional latency result is evaluated on all completed offered order-command
responses. The report MUST also state the timeout fraction; if at least 10% of offered
requests lack a completed response, the p90 ceiling has not been demonstrated. Fast
503 responses may satisfy the literal all-response p90, but such a run MUST NOT be
described as sustaining 500 successful commands/second. Accepted/completed throughput
and rejection fraction must appear beside the latency headline.

### 13.4 Environment and overload evidence

Evidence MUST identify commit, Rust toolchain, release profile, load-generator name and
version, exact invocation/configuration, operating system, CPU model and logical/physical
core counts, RAM, power/thermal mode if known, core affinity, other material co-located
load, server limits, and raw result-artifact locations.

Separately from the canonical run, M3 MUST prove overload behavior with:

1. the paused-engine/full-queue conformance test from section 4; and
2. stepped open-loop probes above 500 RPS until overload is observed or a documented
   local-generator ceiling is reached.

The stepped results MUST report offered, dispatched, completed, HTTP 200, domain-error,
503, timeout, connection-error, admitted-command, and engine-completed rates plus queue
high-water mark. Optional 100K–500K offered-load points MUST be labeled **exploratory**,
not gates or capacity promises.

M3's evidence report MUST explicitly replace or revise the provisional contract after
observing these results. Any proposed new rate, mix, percentile, rejection allowance,
or environment must be written as a new measured baseline, not retroactively used to
change whether the initial 500/p90 run passed.

## 14. Exact non-goals

M3 MUST NOT add, promise, or claim:

- WebSocket market data, trade/BBO/L2 feeds, subscriber sequence numbers, subscriber
  buffering, resynchronization, or slow-consumer handling (M4);
- simulator agents or generated/ingested/matched/egressed order timestamps (M5);
- PostgreSQL, any other database, asynchronous persistence, event sinks, or batching
  to storage (M6);
- Docker, Colima, Kubernetes, pods, load balancers, service meshes, or connection
  poolers (M7+);
- journaling, recovery snapshots, checksums, crash replay, or exactly-once semantics
  (M9);
- authentication, authorization, cancel ownership credentials, balances, positions,
  credit/risk checks, fees, settlement, or rate limits per client;
- TLS, HTTP/2, an API gateway, CORS policy, public-internet deployment, or API keys;
- order amendment, replace, stop, iceberg, pegged, post-only, IOC/FOK, auctions, or
  cross-symbol atomic operations;
- per-symbol worker threads, sharding, shared-book locks, speculative ring buffers,
  busy spinning, thread pinning, or other performance optimization without evidence;
- changing M1 matching, price-time priority, quantity, cancellation, symbol isolation,
  or the settled self-trade policy; or
- claiming the later PRD throughput target or an exploratory 100K–500K probe as an M3
  acceptance threshold.

## 15. Genuine captain decisions

There is no unresolved M3 captain decision in this architecture.

The captain has already decided the only inherited semantic question: cancel an
encountered same-owner resting maker, continue matching the incoming remainder, and
retain earlier third-party fills. The M1/M2 typed result/event schema still needs a
written amendment to encode that settled behavior before v1 is frozen, but no further
policy choice is required from the captain.

The required symbol query parameters, strict ticks-based JSON, finite configuration,
completion-on-engine-result rule, snapshot barrier, and HTTP status mapping are bounded
M3 engineering choices made under the roadmap and accepted ADRs. The evidence-led
post-M3 benchmark revision cannot safely be selected before measurements exist, but it
is a required evidence output rather than a present captain decision.

## 16. Delivery and review implications

Under `docs/DELIVERY.md`, the scenario author MUST differ from this requirement author
and write scenarios before reading production code. The implementer, scenario author,
and reviewer must be three distinct people. The eventual small M3 PR or PR sequence
must retain one coherent externally testable increment and include the written
requirement, independently authored scenarios, actual E2E/status/shutdown/overload
output, validation results, raw benchmark evidence, and the reviewer's two explicit
verdicts: requirement conformance and focused captain attention. The captain alone
approves each merge.

This report authorizes no project code, tests, workflow changes, commits, pushes, or
pull requests.
