# M4 WebSocket market-data scenarios

**Scenario author:** trade-rs M4 independent scenario/test crewmate
**Status:** accepted M4 scenario specification
**Authoring boundary:** authored from the written M4 requirement and the accepted M2/M3
contracts before inspecting any M4 production implementation or implementation branch.
This is an observable-behaviour specification, not test code or an architecture choice.
**Independence record:** the requirement author is `trade-rs M4 requirements crewmate`;
the scenario author is distinct from that author, the implementation author, and the
reviewer, as required by [the delivery contract](../DELIVERY.md).

## Authority and evidence

These scenarios derive from the [M4 requirement](../requirements/M4.md), the roadmap,
the delivery contract, and the accepted M2 and M3 contracts. They define the
client-visible acceptance inventory for M4; the requirement settles the protocol
details that these scenarios intentionally do not select.

Each scenario uses a fresh, explicitly configured server with a power-of-two
market-data ring capacity no smaller than 64 and actual HTTP/1.1 WebSocket
clients unless its setup says otherwise. A successful subscription uses one configured
symbol and records the HTTP upgrade, decoded WebSocket frames, close code/reason where
available, and relevant server counters. Frames are compared as decoded JSON: object-key
order and insignificant whitespace are ignored, while typed values, enum strings, array
order, stream ID, symbol, and sequence are compared. The independently known expected
book is derived from the command fixture, not the feed under test.

`S` denotes the sequence in an initial snapshot. A later live record is consecutive
only when its sequence is exactly the prior live sequence plus one. A reconnect means a
new WebSocket connection that completes its own initial snapshot.

## Lifecycle and subscription

| ID | Stimulus | Required observable result |
|---|---|---|
| L1 | Subscribe to an empty known symbol with a valid upgrade and exact subprotocol. | `101` selects `trade-rs.market-data.v1`; the first and only application frame before later engine activity is one `l2_snapshot` with `reason: "initial"`, empty sides, the configured depth, and the current sequence without advancing it. |
| L2 | Subscribe to a known symbol after a fixture has created a nonempty book, then submit later commands. | The first frame is an authoritative initial top-N snapshot covering the queued prior state. Later visible publications arrive only after that frame and use the same stream ID and symbol. |
| L3 | Keep a successful empty-book subscription open while a successful command has no trade, BBO change, or visible top-N change; then close it. | No placeholder frame is emitted for the silent command and no sequence is consumed. Client close is the only unsubscribe operation and creates no market-data item. |
| L4 | A consumer changes from symbol A to symbol B. | It opens a separate B connection, accepts B's initial snapshot, then closes A. Neither socket changes its selection in place, and each symbol retains its own sequence cursor. |

## Publication order and projections

| ID | Stimulus | Required observable result |
|---|---|---|
| O1 | Submit a command that executes several fills across price levels and changes BBO and visible L2. | One `trade` appears per M2 `trade_executed` in exact M2 effect order, followed by at most one final `bbo`, then at most one final update `l2_snapshot`; their shared sequences are consecutive. |
| O2 | Submit, in sequence, commands that produce trade-only, BBO-only, L2-only, and no visible change cases. | Each command emits exactly the applicable final record types in the required order; a silent case emits none and does not create a sequence hole. |
| O3 | Hold one A subscription open, open a B subscription at a queue barrier between distinguishable A commands, and continue activity on both symbols. | B's first frame captures state after work before its barrier; neither subscription receives data for the other symbol, and opening B changes no A stream behaviour. |
| O4 | Subscribe after the symbol already has a nonzero current sequence, then trigger a live publication. | The initial snapshot reports the current value `S` without consuming one; the first later live record is `S + 1`. |
| O5 | Submit a command whose publication is observable through both its HTTP completion and the subscribed feed. | The engine has assigned and attempted the feed publication before the corresponding HTTP completion is delivered; this does not claim that the peer has read bytes before the HTTP response. |

| ID | Stimulus | Required observable result |
|---|---|---|
| C1 | Build bid and ask books with more levels than configured depth, multiple orders per level, and exact aggregate quantities. | Initial and update L2 records contain exactly the top-N levels, bids descending and asks ascending, with the authoritative per-level aggregate; hidden depth is absent. |
| C2 | Produce empty, one-sided, and two-sided books, including a command that changes a visible level without changing the best price. | BBO and L2 remain coherent with the authoritative projection. Empty sides are represented only by the documented empty arrays/absent BBO side; a visible non-best-depth change produces the required L2 update. |
| C3 | Run partial fills, cancellation, self-trade-prevention cancellation/continuation, market remainder, rejected command, and below-depth-only mutation fixtures. | Trades equal M2 fills; BBO/L2 reflect only final post-command visible state. Rejection and below-depth-only mutation produce no erroneous publication. |

## Loss detection and resynchronisation

| ID | Stimulus | Required observable result |
|---|---|---|
| G1 | Deliberately omit one delivered live frame from a consumer's local transcript while later frames remain observable. | The consumer can detect the nonconsecutive sequence and must treat continuity as lost; it does not accept later data as a repaired stream. |
| G2 | Disconnect a subscriber, execute visible commands during the gap, then reconnect. | The new initial snapshot reflects the current net top-N state after its queue barrier and establishes a new baseline. Lost trade ticks are not replayed. |
| G3 | Replace the process stream identity or send a frame with a different stream ID to a consumer model. | The changed stream ID invalidates continuity even if numeric sequences otherwise appear consecutive; recovery requires a fresh connection. |
| G4 | Cause decode failure, socket loss, or server close after a subscription has begun. | The consumer treats continuity as lost and recovers, if desired, only by a fresh connection and initial snapshot; no in-band resume is attempted. |
| G5 | Run interleaved visible commands for two symbols, introduce a gap only on A, and reconnect only A. | A's recovery does not change B's connection, cursor, or contiguous delivery. Sequences advance independently by symbol. |

## Bounded slow-consumer behaviour

| ID | Controlled setup/action | Required observable result |
|---|---|---|
| S1 | Stall one subscribed client's reads while publishing more records than its configured ring can retain. | The stalled client is terminally disconnected on lag and receives no later application record on that socket; the recorded lag/missed evidence is finite. |
| S2 | After a detected sequence gap, attempt to continue using the old connection without reconnecting. | The server provides no resume token, replay offset, or in-band resync record; the client cannot restore continuity in place. |
| S3 | Reconnect after S2 and place commands before and after the reconnect barrier. | The first new frame is one queue-ordered initial snapshot after earlier work; its receiver covers later publications without duplicate boundary data. |
| S4 | At the minimum valid ring capacity of 64, keep one healthy subscriber promptly reading through an ordinary match that publishes trade, BBO, and L2 records; separately keep another subscriber stalled until lag disconnect. | The healthy subscriber remains contiguous and receives the three ordered records without `1013`/`resync_required`; matching, HTTP completion, and its delivery do not wait for the stalled subscriber. |
| S5 | Repeat connect, stall, overflow/disconnect, and close cycles under the configured limits. | Connection, subscriber, retained-value, task, and missed-item high-water evidence remains bounded by configured finite limits; no unbounded per-client buffer appears. |

## Disconnects and input failures

| ID | Stimulus | Required observable result |
|---|---|---|
| D1 | Drop a subscription normally and separately induce peer reset/write failure while later commands publish. | Each affected connection is removed without retry or replacement; its loss cannot stall healthy clients, matching, or another symbol. |
| D2 | Complete a valid subscription to an otherwise idle symbol, then close the connection before any live publication. | It received exactly its initial snapshot, its receiver is released, and the close consumes no sequence or creates a synthetic update. |
| D3 | With one symbol selected, attempt a dynamic subscribe, unsubscribe, or symbol-change application message. | No selection changes in place. Any post-upgrade text or binary application message is terminal policy close `1008`; it causes no engine mutation or sequence consumption. |

| ID | Stimulus | Required observable result |
|---|---|---|
| F1 | Send missing, duplicate, unsupported, malformed, or multiple subprotocol offers; and separately a missing/incomplete WebSocket upgrade. | The request fails before upgrade with the section-4 status and stable error code (`unsupported_subprotocol` or `upgrade_required` as applicable), no receiver, and no sequence effect. |
| F2 | Send a missing, duplicate, unknown, empty, malformed-percent-encoded, or extra `symbol` query key; a body; or a malformed handshake value. | The request fails before upgrade with `400 malformed_request` (or `404 unknown_symbol` after a valid barrier lookup), no lasting receiver, and no sequence effect. |
| F3 | Exhaust market-data permits, fill the engine queue, and begin drain/close the engine in separate runs before a valid request. | Each run returns the documented immediate `503` stable code (`market_data_overloaded`, `ingress_overloaded`, or `service_unavailable`); it neither waits/retries nor creates a receiver or sequence item. |
| F4 | Use a known route with an unsupported method and send an otherwise valid connection that offers compression. | The method fails with `405 method_not_allowed`; successful M4 upgrades never negotiate compression. |

## Symbol isolation and protocol metadata

| ID | Stimulus | Required observable result |
|---|---|---|
| M1 | Subscribe to two configured symbols and generate records for only one. | Only the active symbol's counter advances and only its connection receives records; the other initial sequence remains unchanged. |
| M2 | Close, lag, or reconnect one of two independently subscribed symbols while commands continue on both. | The unaffected symbol remains live and contiguous; the affected symbol alone establishes a new snapshot baseline after reconnect. |
| M3 | Compare decoded records from interleaved two-symbol activity and repeated subscriptions in one process. | Every record carries version `1`, the one process stream ID, its selected symbol, and a sequence contiguous only within that `(stream_id, symbol)` pair. |

## Shutdown, restart, and terminal conditions

| ID | Controlled setup/action | Required observable result |
|---|---|---|
| T1 | Begin orderly drain with admitted commands, open subscriptions, and a stalled socket. | Admitted commands publish before publishers close; new admission is rejected; closing/aborting slow socket work cannot prevent finite process exit. |
| T2 | Start a fresh process after orderly stop and subscribe before and after its first visible command. | The new process presents a new UUID-format stream ID and per-symbol counters begin at zero; initial snapshots and first live sequences obey the normal baseline rule. |
| T3 | Force lag, write deadline/buffer exhaustion, peer I/O failure, and abnormal engine exit in controlled runs. | Each connection closes with its terminal reason, no socket emits later application data after terminal lag, and all affected resources are released within documented bounds. |
| T4 | Arrange stale frames or state retained by a previous process/session, then create a fresh subscription after restart. | A fresh session never treats old `(stream_id, symbol)` continuity as current and never receives stale frames from the prior process. |

## Prohibitions

| ID | Forbidden observable behaviour |
|---|---|
| N1 | A gap, duplicate, changed stream ID, decode failure, or transport close is silently treated as contiguous or repaired in place. |
| N2 | Different live record types use separate counters, reorder across a command boundary, duplicate a sequence, or leave a sequence hole for a publication. |
| N3 | Activity, lag, closure, or recovery for one symbol advances, leaks into, or stalls another symbol's feed. |
| N4 | L2 omits/creates visible liquidity, has unsorted sides, exposes more than top-N, or conflicts with the BBO/authoritative book. |
| N5 | A slow client grows an unbounded buffer or delays matching, HTTP completion, a healthy subscriber, or shutdown beyond the configured finite bound. |
| N6 | The server offers replay, resume, buffered recovery, or an in-band resync message for a lagged or lost connection. |
| N7 | Invalid route/query/upgrade/subprotocol/input is admitted as a mutable engine action, creates a lasting receiver, or consumes a sequence. |
| N8 | Sequence wraps on exhaustion, a restarted process knowingly reuses its stream ID, or continuity crosses process epochs. |
| N9 | A terminal/stale session receives later application data or is used as the source of a new subscription baseline. |

## Completion boundary

This scenario document defines the M4 acceptance inventory; it does not extend M4's
scope to new infrastructure or benchmark claims. The implementation PR supplies the
E2E, property, lifecycle, and performance evidence for every ID above, with the
delivery-role separation required by the delivery contract.
